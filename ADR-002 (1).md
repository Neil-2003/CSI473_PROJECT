# ADR-002: Pattern and Framework Selection

CSI473 · Laboratory 9 · Semester 1, 2026/27 · Project: UB Student Accommodation System · Team 14

| Field | Details |
|---|---|
| **Decision ID** | ADR-002 |
| **Date** | 9 October 2026 |
| **Status** | Accepted |
| **Issue** | Which patterns and framework should implement the core allocation workflow, given ADR-001 (modular monolith) and Lab 8 (data, API, failure design)? |
| **Alternative A (rejected)** | Plain Java, manual DI, hard-coded rule checks. No framework; BR-01/BR-02 as a linear if/else sequence inside `AllocationService`; manual transactions and HTTP handling. |
| **Alternative B (selected)** | Spring Boot with Repository, Strategy and Ports-and-Adapters. Rules as `AllocationRule` strategies; persistence behind repository ports; core operation exposed via `AllocationUseCase`; Spring DI and `@Transactional`. |
| **Decision** | Alternative B is selected. |

Traceability: DP-01 – DP-05 (`docs/pattern-decisions.md`), QS-03, QS-04, AD-01.

## Rationale

1. **DP-01:** Repository ports decouple the core from SQL.
2. **DP-02:** Strategy makes BR-01 and BR-02 independently testable and extensible.
3. **DP-03:** Ports-and-adapters keeps HTTP out of the domain.
4. **DP-04:** The core operation is callable via the port without HTTP (demonstrated by `AllocationSmokeTest` in `src/core-skeletons/`).
5. **DP-05:** `OccupancyTracker` is a single domain service used by the rule and the admin view.
6. **QS-03:** `@Transactional` supplies the boundary required by the failure-recovery design.
7. **Feasibility:** Spring's DI, transaction and test support reduce implementation risk within the semester.

## Transaction and Rule-Order Rules

- **Rule order.** `AllocationService` evaluates rules in registration order and stops at the first failure: BR-01 (`RULE_001`) before BR-02 (`RULE_002`). The first failing rule therefore decides the error code returned by the Lab 8 API contract.
- **Isolation.** `allocate()` runs in one transaction at `READ COMMITTED`. Because the capacity check (BR-02) reads derived occupancy and the save happens afterwards, a second concurrent allocation could otherwise slip in between. The Phase 2 SQL adapter therefore reads the room with `SELECT … FOR UPDATE` inside the transaction, so concurrent allocations for the same room serialise and the capacity check is effectively re-run on committed data. On SQLite, the single-writer lock gives the same serialisation. BR-01 additionally has the partial unique index from the Lab 8 data model as a database-level backstop.
- **Occupancy reads.** `OccupancyTracker` is read-only and joins the caller's transaction; it never opens its own.

## Positive Consequences

- BR-01 and BR-02 are independently testable and extensible.
- The core workflow is testable without a database or web server.
- Transaction boundaries are declarative and match Lab 8.
- Traceability from QS-03 and QS-04 to concrete classes is direct.

## Negative Consequences

- Spring annotations couple wiring classes to the framework, a partial compromise of the ports-and-adapters ideal.
- Learning curve for members unfamiliar with Spring.
- Larger runtime footprint than plain Java.
- More classes than Alternative A (one interface plus one class per rule).
- Row locking adds a small cost to each allocation (acceptable at the expected allocation volume).

## Risks and Reconsideration Triggers

| Risk | Trigger for reconsideration | Owner |
|---|---|---|
| Framework coupling in core | If `AllocationService` cannot be unit-tested without Spring, switch tests to plain constructor wiring (already possible today). | Allocation module lead |
| Transaction behaviour not as expected | If `@Transactional` plus the row lock does not give the isolation needed by the Lab 8 concurrency test (QS-03), use manual transaction management or raise the isolation level. Acceptance test: two simultaneous `allocate()` calls for the last space, exactly one succeeds. Due: Phase 2, first database sprint. | Persistence lead |
| Team unfamiliarity with Spring | If the team struggles with Spring DI, fall back to manual wiring while keeping the port interfaces. | Team lead |
| Strategy list grows unwieldy | If rule ordering or count becomes hard to manage, introduce a rule registry/ordering mechanism. | Allocation module lead |
