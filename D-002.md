# Decision Record: D-002

CSI473 · Laboratory 4 · Semester 1, 2026/27

| **Field** | **Details** |
| :--- | :--- |
| **Decision ID** | D-002 |
| **Date** | 21 August 2026 |
| **Issue** | How should the relationship between a student and a room be represented and persisted to ensure accuracy? |
| **Alternative A (rejected)** | Store a `roomId` as a direct attribute on the `Student` class. |
| **Alternative B (selected)** | Create a separate `Allocation` class to represent the association. |
| **Rationale** | Alternative B is selected because it provides a more flexible and historically accurate model. An `Allocation` entity can store additional information such as the date of allocation, the admin who made the allocation, and (in future) a status such as Active, Completed, or Cancelled. This supports use cases that require viewing a student's full accommodation history and auditing decisions. It also makes enforcing the "one active allocation per student" rule (BR-01) cleaner, as the system can query for active `Allocation` records rather than checking a nullable field on `Student`. |
| **Consequence accepted** | More complex queries are needed to get a student's current room (must query active `Allocation` records rather than reading a single attribute). This is a common and accepted pattern that improves the model's integrity and expandability. |

# Decision Record: D-001

| **Field** | **Details** |
| :--- | :--- |
| **Decision ID** | D-001 |
| **Date** | 21 August 2026 |
| **Issue** | Should room occupancy be a derived value (calculated on demand from active allocations) or a stored, separately-maintained value on `Room`? |
| **Alternative A (rejected)** | Add an `occupancy` counter attribute directly on `Room`, incremented/decremented whenever an allocation is created or ended. |
| **Alternative B (selected)** | Keep occupancy as a derived value, calculated by `Room` from its active `Allocation` records, and maintain a separate `OccupancyRecord` class purely for historical tracking. |
| **Rationale** | Alternative B avoids a duplicated, cache-style counter that can drift out of sync with the actual set of allocations if an update is missed (violating BR-06). Deriving occupancy directly from active allocations keeps a single source of truth. `OccupancyRecord` is kept as a separate class because it serves a different purpose — historical/audit trail with start and end dates — rather than a live counter. |
| **Consequence accepted** | Calculating occupancy requires a query over `Allocation` records rather than a simple attribute read, which is an acceptable trade-off for data consistency at the expected scale of the system. |
